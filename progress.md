## 2026-09-26 — Customer location capture (GPS + OpenStreetMap), branch truthfulness

- **Why**: the app shipped hardcoded fake location. `LocationNotifier.useCurrentLocation()` returned the literal string `"COMSATS University, Abbottabad Campus"`, `LocationState` defaulted to `"COMSATS Abbottabad, Phase 2"`, and the address form asked customers to type latitude and longitude by hand. Nearest-branch selection was therefore decorative.
- **Migration `branches_add_coordinates`**: added nullable `public.branches.latitude` / `.longitude` (`numeric`) and seeded them — `ABT` = `34.204008, 73.238723` (Ayub Medical Complex area, confirmed via Nominatim) and `MSH` = `34.328686, 73.199313`. **The Mansehra pair is a city-centre placeholder, not the real shop** — that branch row still carries a `TODO - add real Mansehra branch address` address and a dummy phone.
- **Honest nearest-branch**: new `BranchSelection` returns `isNearestToAddress`, and `CheckoutState.branchIsNearest` is the single value allowed to decide the checkout label. A branch is only called "nearest" when both the address and the branch rows have coordinates; an unpinned address now selects **no** branch (the customer picks) instead of silently taking the first one alphabetically.
- **New `lib/features/location/`**: `LocationRepository` composes a `DeviceLocationSource` (real GPS via `geolocator ^14.0.3`) with an `AddressTextLookup` (OpenStreetMap Nominatim over `http ^1.2.0`, no API key). Everything else in the app talks to those interfaces, which is why the whole thing is testable without a phone.
- **Location is optional, by construction**: permission denied / blocked-forever / location services off / GPS timeout / bad fix all raise `LocationCaptureException` with a message the UI shows, and manual entry keeps working. A **reverse-geocode failure is deliberately not an error** — the GPS pin is kept and only the address text stays empty, so a good fix is never thrown away because a lookup failed.
- **Address form**: the manual latitude/longitude fields are gone, replaced by a `Use My Current Location` button that fills the editable address text, shows a `Pinned at ...` line, and on a blocked permission offers an `Open Settings` button.
- **`LocationSelectionDialog` cleaned up**: dropped the four invented saved addresses (`COMSATS Abbottabad, Phase 2`, `Mansehra University Road`, `Shaheen Chowk, Abbottabad`, `Supply Bazaar, Mansehra`) in favour of the customer's real saved addresses, removed the fake 600 ms "locating" delay that closed the dialog even when permission was denied, and made picking a saved address keep its stored pin via `LocationNotifier.applySavedAddress`.
- **`BranchCatalog`**: `OrdersRepository.fetchBranches()` now returns a catalog that reports `usedFallbackData`. The bundled fallback branches have non-UUID ids (`branch_abbottabad`) which would fail the `orders.branch_id` foreign key, so the flag exists so the UI can say the data is not live instead of pretending.
- **Platform permissions**: `ACCESS_FINE_LOCATION` / `ACCESS_COARSE_LOCATION` in `AndroidManifest.xml`; `NSLocationWhenInUseUsageDescription` in `ios/Runner/Info.plist`.
- **Tests**: 59 passing across the location and branch files. `flutter analyze` — No issues found.
- **Correction to the 2026-09-26 RLS entry below**: it says "14 policies". The migration actually creates **13** (5 on `admin_users`, 4 on `categories`, 4 on `menu_items`).
- **Correction to the 2026-09-26 RLS entry below**: the `updated_at` profile bug is now **fixed** — the invalid key was removed from `ProfileRepository.updateProfile()`.
- **Still open**: `nominatimUserAgent` in `lib/core/providers/location_provider.dart` carries a placeholder email and must be replaced with a real monitored contact before release (Nominatim's usage policy). The real Mansehra shop address and coordinates are still unknown. GPS has not been exercised on a physical device.


## 2026-09-26 — Supabase RLS lockdown (admin_users, categories, menu_items)

- **Root cause found**: `menu_items` had RLS *enabled* but *zero* policies, so every read returned 0 rows and the app silently fell back to the 14 bundled mock items (`lib/features/menu/data/menu_repository.dart:17`). The 88 real rows were invisible.
- **Security hole closed first**: `admin_users` and `categories` had RLS **disabled** with full `INSERT/UPDATE/DELETE` grants to `anon` and `authenticated`. Since self-signup is open, anyone could have signed up and inserted their own `admin_users` row with `role='owner'` — full privilege escalation. This had to be fixed *before* writing any role-checking policy, or those policies would inherit the hole.
- **Added helper functions** `public.is_owner()` and `public.is_staff()` (`SECURITY DEFINER`, `stable`, `search_path = public`). `SECURITY DEFINER` is required so they can read `admin_users` after its own RLS is enabled, and so the "owner reads all admins" policy doesn't recurse into itself.
- **Seeded the first owner** so admin management isn't orphaned: `6c880430-3a53-40f5-b2d2-f1d1595328b0` (Muhammad shahzeb), `role='owner'`, `branch_id=null`.
- **Applied 14 policies** across the three tables: `admin_users` self-read for signed-in users + owner-only insert/update/delete; `menu_items` and `categories` public read with staff-only writes. `menu_items` read filters to `is_available = true` for customers while staff see the full catalog.
- **Lockout guards**: an owner cannot delete their own row or change their own role away from `owner` — otherwise the last owner could permanently orphan admin management.
- **Verified**: RLS on for all 3 tables, 14 policies present, both functions created, 88 menu items + 15 categories intact, and confirmed the `anon` Postgres role reads 88 menu items through the public policy. `anon` appears on no insert/update/delete policy for any of the three tables, so anonymous writes are denied by default.
- **Decisions**: one shared menu for both branches (no `branch_id` on `menu_items`/`categories`) — Abbottabad and Mansehra use the same catalog. Menu stays publicly readable so customers can browse pre-signup. No Dart changes needed; the policy does the filtering that `MenuRepository.fetchMenuItems()` was missing.
- **Architecture confirmed**: Flutter app is customers + riders only; the owner/manager/staff admin panel is a **separate Next.js codebase, not in this repo**. The `profiles.role` check constraint (`customer`/`rider`) is therefore correct as-is and should not be widened — admin status lives only in `admin_users`. Flagged that the panel must use the **publishable key** (legacy name: `anon`), never the **secret key** (`sb_secret_...`, legacy `service_role`), because the secret key bypasses RLS entirely and would void every policy applied today.
- **Naming correction**: `anon` / `service_role` are the *legacy* key names; current Supabase terminology is **publishable key** / **secret key**. The Flutter app was already migrated to `publishableKey` on 2026-09-13. Noted that the `anon` Postgres *role* name is unrelated to the key and unchanged.
- **Deferred by decision**: 10 tables still have RLS disabled (`branches`, `orders`, `order_items`, `order_status_history`, `transactions`, `vouchers`, `voucher_redemptions`, `loyalty_ledger`, `rider_details`, `rider_assignments`) — to be locked one at a time as each feature is built. `orders` and `transactions` are the priority (customer addresses, payment records).
- **Owner moved off the app's customer test login**: initially seeded `razashahzaib119@gmail.com` (the Flutter app's everyday customer test account) as `owner` because it was the only account with a `profiles` row. That was the wrong default — the app is customer/rider only, so an owner on a customer test account means the customer test session passes every admin check and can bypass every policy, and customer-side security testing becomes meaningless. Swapped the owner onto the dedicated panel login `admin@mrpizza.com` (`6c90ef98-1036-447c-a26b-7e1d42a00fa9`, `full_name` = "Panel Owner") and removed the admin row from the gmail account. Verified: exactly one owner, app test account is now a plain customer with no admin powers.
- **Account audit**: confirmed 3 distinct `auth.users` rows (no duplicates, contrary to suspicion). `admin@mrpizza.com` and `admin123@mrpizza.com` were both created directly in the Supabase dashboard and therefore have **no `profiles` row** — since there is no signup trigger, `ProfileRepository.fetchProfile()` returns `null` for both (`profile_repository.dart:8`), which is what made two different accounts look like one in the app.
- **Bug found, not yet fixed**: `ProfileRepository.updateProfile()` writes an `updated_at` key (`profile_repository.dart:20`) but the `profiles` table has no such column (only `id`, `role`, `full_name`, `phone`, `created_at`). Profile saves from the app will fail with a database error.
- **New file `admin-access-control-notes.md`**: reference doc covering the add-an-admin runbook, role capability table, every policy applied, the shared-menu decision, the admin/app account separation rule, gotchas, the unlocked-table register, and the ordering recipe for future tables.
- **Left untouched per scope**: the Flutter app's rider side. `lib/core/routing/route_guard.dart:8-16` still returns `true` unconditionally and `lib/core/providers/role_provider.dart:12` is still a hardcoded in-memory `customer` — both pre-existing stubs, to be wired to the real `profiles.role` when rider work starts.
